## 2. 卡面文案长度的真机标定

### 几何

| 项 | 值 |
|---|---|
| 文字区（`.ctext`） | **84 × 65** 布局 px |
| 基准字号 / 行高 | 10.5px / 1.26（13.23px） |
| 可容行数 | 65 ÷ 13.23 ≈ **4.9 行** |
| 每行全宽字数 | 84 ÷ 10.5 = **8.0 字** |
| 缩字下限 | 8.5px（`fitCardText` 逐档 0.5px 降到 8.5 为止） |

### 注入实测（全宽汉字最坏情况，无空格可断行）

| 字数 | 实际字号 | 缩了几档 | 结果 |
|---|---|---|---|
| 16 / 20 | 10.5 | 0 | ✅ 放得下 |
| 24 / 26 / 28 | 10.5 | 0 | ✅ 放得下 |
| 30 / 32 / 34 | 10.5 | 0 | ⚠️ 出现 **1px** 溢出（落在 `fitCardText` 的 ±1px 容差里，肉眼不可见，但已开始依赖容差） |
| 36 / 40 | 9.5 | 1 | ✅ 靠缩字放得下 |
| 45 / 50 | 8.5 | 2 | ✅ 靠缩到下限放得下 |
| **58** | 8.5 | 2 | ❌ **缩到底仍然裁字** |

于是「必须缩字」的分界点在 **29 单位**，「彻底裁字」的分界点在 **58 单位**。

### 现有卡牌的分布

用「全宽字 = 1.0，ASCII = 0.5，空白 = 0.34」折算：

```
最长 25.2 单位（悔恨）  ← 其余全部 ≤ 22.5
```

## 3. 补上的门禁

在 `tools/test.mjs` 的 B 段（数据自洽性）里新增一条断言：

```
卡面文案长度都在预算内（≤ 28 单位，最长的 悔恨 是 25.2）
```

**阈值语义**：28 单位 = **必须在基准字号（10.5px）下放得下**，不许依赖缩字。
（29 单位起就会触发缩字 —— 字变小、可读性下降，应该是作者有意识的取舍，而不是不小心写长了。）

实测验证过这条门禁**真的会拦**：注入一张 43.2 单位的合成卡，测试立刻：

```
❌ 卡面文案长度都在预算内（≤ 28 单位，最长的 测试超长文案 是 43.2）
```

要写更长的文案时，请**先真机确认**，再有意识地调高 `tools/test.mjs` 里的 `TEXT_BUDGET`。
常量旁边写了完整的标定数据与推导过程。

## 4. 真机测量的一个陷阱（写新审计脚本时会踩）

`#stage` 用了 `zoom` 做整体缩放（见 README「界面自适应」），于是：

| API | 返回单位 |
|---|---|
| `getBoundingClientRect()` | **视觉像素**（已被 zoom 放大，÷ 2.19 才是布局值） |
| `clientHeight` / `offsetHeight` / `clientWidth` | **布局像素**（未缩放） |

**同一个元素上混用这两种单位会得到荒谬结论。** 我在标定时先写了一版混用的脚本，
结果「所有卡都超出 3.86 行」，而实际 0 张溢出 —— 因为 `getBoundingClientRect()` 量到的比
`clientHeight` 大 2.19 倍。

规则：**比较两个尺寸就用同一种 API**。量溢出用 `scrollHeight vs clientHeight`，
量位置用 `getBoundingClientRect` 但两边都用量出来的值。

## 5. 手机端的能力边界（对指南 §9 的修正）

指南 §9 写的是「手机端不方便跑 npm，所以 build→test→提交 以桌面端为准」。实际情况：

| 能力 | 状态 | 备注 |
|---|---|---|
| `node tools/build.mjs` | ✅ 可以 | Node 24 在容器里；依赖走 `/root/abyss-test/node_modules` 回退 |
| `node tools/test.mjs` | ✅ 可以 | **181 项全绿**（当时） |
| `npm ci` | ❌ 不行 | `/sdcard` 是 FAT 文件系统，**不支持符号链接**，npm 的 `.bin` 建不出来 |
| `git ls-remote` / `fetch --depth 1` | ✅ 可以 | 网络抖动时会失败，重试即可 |
| `git clone`（全量） | ⚠️ 不稳定 | 传输量大时容易 `GnuTLS recv error (-110)` |
| `git push` | ❌ 不行 | **容器内没有 git 凭证**（不是被墙，报错是 `could not read Username`） |

所以正确的表述是：**手机端能改、能 build、能 test，但推不上去。**

为此加了两个脚本：

- `tools/sync.sh pull|status` —— 拉取线上（优先 `git fetch --depth 1`，失败退 codeload tarball）
- `tools/handoff.sh` —— 把改动打成 `git diff` 补丁，交给有凭证的一端 apply + push
  （`sw.js` 的 `VERSION` 是构建期盖章的、跨机器必然不同，已排除出补丁）

现在的行为是「数量不对齐就整体拒绝，退化成重开这场战斗」—— 安全的。
但「删掉某个敌人会让老存档打不开」这点仍在。

若想彻底解决，可选方案是**把敌人定义快照进存档**（name/sprite/hp/moves），
这样完全不依赖 `ENEMIES` 表。代价是平衡性调整不会作用到进行中的战斗。
**这是设计取舍，不建议我单方面改**，留给桌面端定。

> **桌面端答复**：同意这是设计取舍，**本次不动**。理由：现在这条路径已经是"安全失败"
> （要么正常恢复、要么重开这一场），不会让存档损坏或错乱；
> 而"快照进存档"会带来一个真实的坏处 —— 玩家打到一半的战斗不吃平衡性调整，
> 出问题时更难解释。除非将来真的频繁改敌人表，否则维持现状。

**桌面端复核（2026-10-12）——真凶不是 rollup，是文件系统的目录顺序**

~~`stampServiceWorkerVersion()` 对 `precache.json + index.html + css + dist/bundle.js` 算 SHA1，
其中 `bundle.js` 由 rollup 产出 → **依赖版本不同就得到不同哈希**。
实测：我用容器里的 rollup 算出 `abyss-4a79cc2ad5aa`，**和线上部署的完全一致**；
而仓库里提交的是 `abyss-b042b895292d`。也就是说 CI 是确定的，是**本地环境**与锁文件不一致。
影响：本地每次 build 都会弄脏 `sw.js`；另外每次部署会因为哈希变化白白失效一次全量缓存。
锁死 rollup 版本（确保 `npm ci` 与本地一致）即可。~~

手机端的观察（哈希确实不一致）是对的，但**归因错了**。桌面端实测：

| 检查 | 结果 |
|---|---|
| 锁文件里的 rollup | `4.64.5` |
| 本地实装 rollup | `4.64.5` |
| 结论 | **版本本来就一致**，所以不是依赖版本的问题 |

真正的原因：`buildPrecache()` 用 `walk()` 递归扫目录，而它按 `readdir` 的**返回顺序**追加 ——
这个顺序是**文件系统相关**的（NTFS 大致按名字，ext4 是哈希序）。

直接对证线上与本地的 `precache.json`（集合完全相同、149 项，**只有顺序不同**）：

```
线上(Linux): .../sprites/golem.png → grave_cross.png → gravestone.png → guard.png
本地(NTFS) : .../sprites/golem.png → gravestone.png → grave_cross.png → guard.png
                                     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 这两项换了位置
```

`grave_cross` 与 `gravestone` 只是恰好被这两种文件系统排到了相反的位置。
**集合一样、字节不同 → `precache.json` 变了 → SW 版本哈希必然不同。**
这跟 rollup、跟环境是否"干净"都无关，换台机器就会重现。

**已修**：`build.mjs` 改用 `sortedWalk()`（码位序 `sort()`，不依赖 locale），
`buildAssetMap()` 也一并改成有序 —— 后者决定单文件版里资源表的键顺序，同样需要确定性。
`tools/test.mjs` H 段加了一条断言盯住「清单必须按码位序排列」，
并已用"退回 `walk()`"的对照实验验证过它**真的会拦**（`第 35 项：anvil.png 应为 sprites.json`）。

顺带修掉一个手机端补丁**引入的新问题**（见 §9）。

## 9. 桌面端复核：dev-agent 改法漏了一处（会导致线上 404）

手机端把 `js/dev-agent.js` 从线上产物里摘掉，方向完全正确 ——
但它漏了一个地方：**`precache.json` 里仍然引用着 `./js/dev-agent.js`**。

`buildPrecache()` 的排除黑名单只有 `node_modules/.git/.github/tools/dist/_site` 和几个文件名，
`js/` 目录下的 `dev-agent.js` 照样会被扫进清单。而 workflow 的 rsync 已经把它排除出站点，
于是：

```
Service Worker 安装时按 precache.json 逐条 add()
  → ./js/dev-agent.js 在站点里不存在 → 404
```

这正是 H 段本来要防的那类问题（当年 1156 条 `node_modules` 也是同样的机制）。
桌面端用真实的站点组装语义复现了它：

```
站点里 js/dev-agent.js 存在: False
precache 引用但站点里没有的条目数: 1
   缺: ./js/dev-agent.js
```

**已修**：`build.mjs` 新增 `PRECACHE_SKIP_DEV_ONLY = new Set(['js/dev-agent.js'])`，
并且测试里把「build 的排除清单 / workflow 的 rsync 排除 / index.html 是否写死」
**三处绑成一条断言** —— 任何一处漏掉都会红：

| 故意制造的错误 | 测试的反应 |
|---|---|
| build.mjs 忘了排除 | ❌ 清单里没有多余条目 / 预缓存清单里不含只在本地开发用的文件 |
| workflow 忘了排除 | ❌ workflow 的站点组装排除了 js/dev-agent.js |
| index.html 又写死它 | ❌ index.html 不再写死调试代理 |
